# W10/W12 host candidate

Reviewable local source, **not applied**. The agent has not connected to production, installed files, migrated permissions, changed a firewall/SSH configuration, stopped a supervisor, retired sync or started a new service. G1 remains blocked. `render` writes only a new local output bundle. All other commands default to read-only planning; stateful execution requires independent Linux root, a separately authorized operator, fresh scoped pinned evidence and explicit `--execute`.

Requirements: Python3.11+ standard library. Root Linux checks use existing `docker inspect`/image/network inspection, `docker compose config --quiet`, `systemctl show`, `sshd -t/-T`, `systemd-analyze verify`, `iptables/ip6tables -S`; they never run Docker create/run/pull/build. Do not run a candidate as part of this implementation review against production. On non-Linux/non-root hosts, preflight returns a blocker without running host commands.

## Offline example

The example uses documentation-only IP addresses, zero identity/inode hashes, unknown consumers, null image digests and null evidence. It is designed to render for review and **fail preflight**. It is not a production configuration.

```sh
python3 -B ops/host-hardening/hardening.py render --config ops/host-hardening/config.example.json --bundle /new/local/review-bundle
python3 -B ops/host-hardening/hardening.py preflight --config /etc/chisa-hardening/change.json --bundle /opt/chisa-review/bundle
```

`render` emits 13 artifacts plus a manifest: precise dual-stack SSH/source rules, input/forward firewall rules and exact inverses, source-isolated service/account policy, Compose JSON, proxy config, gateway config/source, two Dockerfiles, systemd unit, exact UID/HOME mapping and sync retirement plan. It rejects mutable image references, root API, broad privileged mounts, duplicate paths/ports, shared-service mutations, unknown broker channels, mismatched account subnets and unsafe paths. Missing operator digests remain obvious placeholders in the rendered candidate and block preflight. No secret values enter these artifacts.

The manifest pins every artifact and the full operator configuration excluding the **evidence references only**. Evidence references must be filled after render because they attest the bundle digest; excluding references avoids a circular hash. Machine/binding/path/mount/UID/image/network/port/inventory choices remain part of the digest. Any source renderer/gateway change also changes generated bytes, and verification rejects stale or extra artifacts.

## Independent authority and evidence

Stateful commands require canonical root-owned non-writable ancestors, bounded single-link regular records and exact SHA256 references. No record is created by this tool, and it cannot infer acceptance from a candidate's own successful unit tests. Every evidence record contains:

```json
{"version":1,"kind":"g1","change_id":"reviewed-change","machine":{"machine_id_sha256":"64hex","boot_id":"exact-boot"},"bundle_sha256":"64hex-of-rendered-manifest","created_at":"timezone-qualified-date-time","expires_at":"timezone-qualified-date-time","reviewer":"independent-reviewer","requested_by":"different-deploy-operator","artifacts":[{"name":"offsite_commit","path":"/etc/chisa-evidence/offsite-commit.json","sha256":"64hex"}],"checks":{}}
```

Validity is at most two hours; referenced artifacts are independently root-owned, hash-pinned, verified within that record's window, and match machine/change/reviewer. References cannot point to API-writable records, another change, stale boot, a symlink/hardlink, a default all-green template or a different bundle.

Required kinds:

- `g1`: exact `offsite_commit`, `isolated_verification`, `production_drill`, `monitor_delivery` artifacts. The same immutable restore-point ID must appear in offsite/verify/drill; offsite failure domain and recovery host are independent. Production drill explicitly passes real application smoke, UID/ACL/xattr/lease mapping and rollback, with measured RPO≤3600s/RTO≤14400s; monitor receipt is independently confirmed. `ops/recovery verify` alone always has `production_drill_passed=false` and cannot satisfy this gate. These attestations need the real W01 operator/reviewer; local tests never mint them.
- `administration`: fresh second non-root session, sudo, host-key hash, source allowlist, IPv4/IPv6, console and rollback; exact configured admin and host key. `reviewer` must differ from `requested_by`.
- `fence`: admission closed, all eight writer classes, durable generation, no old namespace writer, supervisors masked and consumer inventory verified. Exact current/historical writable-data container IDs and exact API/sync/scheduler supervisors are required. Actual daemon inspection must show all relevant containers stopped, not paused/restarting and restart=no. Every supervisor must be inactive and masked; a stopped old API with `unless-stopped` still blocks. Missing PID in current namespace is never proof.
- `acceptance`: final image/SBOM scan, API no-daemon, nonroot restart, UID/HOME mapping, provider/shell/JSON worker, HTTP/WS/SSE/upload, account isolation, actual runtime gateway integration, cleanup recovery, rollback candidate, proxy syntax, exact egress policy and applied isolation firewall. Its immutable image set must equal the configuration.

These contracts do not define a new way to approve production. They consume separately authorized, independently reviewed actual evidence. In this task the real evidence is missing; defaults block.

## Stateful candidate operations

Every command below is a candidate for **later explicitly authorized** maintenance only. Without `--execute`, it reports a plan after checking gates and does not create even its permanent lock. The exact protected state path is `/var/lib/chisa-deployment/<change_id>`, below a separately provisioned root-owned private directory. It is not automatically created from an arbitrary API path.

```sh
python3 -B ops/host-hardening/hardening.py apply --config /etc/chisa-hardening/change.json --bundle /opt/chisa-review/bundle --state /var/lib/chisa-deployment/reviewed-change
python3 -B ops/host-hardening/hardening.py migrate-ownership --config /etc/chisa-hardening/change.json --bundle /opt/chisa-review/bundle --state /var/lib/chisa-deployment/reviewed-change
python3 -B ops/host-hardening/hardening.py retire-sync --config /etc/chisa-hardening/change.json --bundle /opt/chisa-review/bundle --state /var/lib/chisa-deployment/reviewed-change
python3 -B ops/host-hardening/hardening.py rollback --config /etc/chisa-hardening/change.json --bundle /opt/chisa-review/bundle --state /var/lib/chisa-deployment/reviewed-change
python3 -B ops/host-hardening/hardening.py restore-ownership --config /etc/chisa-hardening/change.json --bundle /opt/chisa-review/bundle --state /var/lib/chisa-deployment/reviewed-change
```

`apply` installs only four fixed allowlisted files: candidate Compose config, candidate systemd unit, public gateway config and proxy config. It does not start/reload/enable a service, install SSH, run firewall rules or mutate Docker. The permanent flock is retained by inode across retries; backed-up before bytes and a journal are private and fsynced before writes. Each install has before/after digest CAS. A crash preserves its state, and rollback accepts only original or recorded candidate bytes, refusing a newer foreign modification. It restores original modes, never unconditionally overwrites a shared file and never enables old high-privilege API. Gateway/proxy public config is root-owned readable; private Compose/state remains0600.

`migrate-ownership`/`restore-ownership` target only the exact enumerated directory inode/device and old/new UID/GID/mode. They do not descend recursively, change ACL/xattr or invent new runtime identity. The isolated mapping acceptance must prove child/native history/runtime ownership is compatible; unknown/replaced data refuses. Changes are journaled under the same guard. It is not a blanket `chown -R` workaround.

`retire-sync` requires `retire=true`, zero independently reviewed consumers, a full actual fence, exact immutable sync image/mount/network and inactive+masked current/historical supervisors. It persists retirement state and masks/stops the exact configured legacy supervisor to keep it fenced; it does **not** delete its container, network, keys, workspace or staging. It does not automatically revive any old supervisor on rollback. The public32768 filter is render-only and separately applied/verified by the operator; observed loopback/dual-stack/external/restart tests remain required. Stopping only Docker while systemd is `Restart=always` is rejected.

## SSH, firewall and rollback

SSH/firewall are **render-only**. Source rules cover exact IPv4 and IPv6 allowlists and destination/port. Default source routes are rejected. SSH disables root/password/keyboard/agent/X11/TCP forwarding, uses exact `AllowUsers user@CIDR`, and includes Match contexts. The full chosen sshd configuration must include the candidate in the correct precedence; preflight tests `sshd -t` and `-T -C user,host,addr,laddr,lport` rather than declaring a successful parse equivalent to a safe management channel. Non-root second-session/sudo/console evidence must exist before installing/reloading this candidate outside the tool.

Docker forwarding rules target the observed `DOCKER-USER` iptables path using connection original destination, preserving published32768→2222 semantics. They do not rely only on UFW/INPUT. Native nft deployments are rejected pending an adapter. No chain flush or global policy reset is emitted. Rules for unrelated shared ports remain unchanged; new per-source candidate isolation denies host/cross-account management access and allows only operator egress and gateway paths. Exact inverse commands remove only the change's own commented rules, not all existing protection.

The separately reviewed console rollback must restore exact old SSH/forwarding configuration without opening all ports. Upstream firewall rule IDs and both external address families must be inventoried. API identity/HOME or database rollback additionally needs a fresh full writer fence; switching an image cannot restore data compatibility by itself.

## Validation and limits

```sh
python3 -B ops/host-hardening/tests/test_hardening.py
node --test ops/deployment/preview-gateway.test.mjs
# root Linux isolated temporary fixture; no real systemctl/docker calls:
python3 -B ops/host-hardening/tests/linux_guard_contract.py
```

The cross-platform tests use temporary fake data, real manifest/hash/CAS/journal logic and injected read-only daemon receipts. Windows cannot prove Unix owner/mode/flock/directory-fsync behavior; that is tested separately in the root Linux `/run` fixture. Syntax/readiness failures and partial journals are preserved as blockers. The gateway uses local real sockets with fixture identity; actual Docker egress/DNS/SSH/HTTPS, shared proxy/CDN, per-account networks, authority publisher/runtime consumer and production G1 are still independent acceptance gates.
