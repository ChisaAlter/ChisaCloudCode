# 保留 VPS 云端开发并新增 SSH 本地开发

日期：2026-10-25
状态：已完成双模式源码实现、自动化验证、本机构建及 2026-10-25 隔离 Windows + VPS 实机验收。真实 SSH、文件/Git/命令、VPS CC 工具、取消/服务中断恢复与原生隧道进程已通过；未部署生产或安装系统 SSH 服务。正式桌面登录/UI、专用账户 ACL 和生产账号网络仍需部署后验收。使用方式见 [SSH 本地指南](../../architecture/ssh-local-workspaces.zh-CN.md)。

## 1. 目标与范围

在当前 ChisaCloudCode 中增加项目级的开发位置选项：

| 项目模式 | Claude Code / 登录 / 会话记录 | 源码、Git、构建、测试 | 桌面关闭后的行为 |
| --- | --- | --- | --- |
| 云端 VPS（现有默认） | VPS | VPS，沿用当前容器、会话工作区和改动集成 | 保持当前云端运行行为 |
| SSH 本地（新增） | VPS | 经 SSH 操作 Windows 上选定的项目目录 | 应用管理的隧道断开，本地执行不可用 |

新增能力以普通 SSH 为基础。Windows 只需要 OpenSSH Server、PowerShell 和项目自己的工具链，不安装 Claude Code，不部署新的本地 MCP/HTTP 服务，不建立源码镜像或实时同步。当前产品内部已有 CC 项目工具接口，可以保留并让它通过 SSH 调用；这不增加 Windows MCP 网关。

源码的唯一工作副本可以留在 Windows，但 CC 按需读取的文件内容、日志和补丁会经过 VPS 并进入会话；连续读取可能累计覆盖整个仓库。因此目标是不强制整体复制仓库，不承诺源码零外传。

第一版完成：接入已有本地目录、CC 读写/搜索、命令行构建/测试/运行、文件树与编辑器、基础 Git 和命令终端。Windows 桌面 UI 自动化、宿主强沙箱、本地会话 worktree/集成、Web 预览反向代理、SSH 模式的其他 AI 提供商留待后续。云端项目继续使用现有能力。

## 3. 技术路线

### 3.1 执行链路

```text
桌面界面 ──现有 HTTPS / WebSocket──> VPS 应用服务 + Claude Code
                                         │
                                  新增 SSH 传输适配器
                                         │
                               Windows OpenSSH Server
                                         │
                               选定目录 + Windows 工具链
```

笔记本在 NAT 后时，由桌面端发起反向 SSH 隧道：

```text
Windows ssh.exe → VPS 受限 SSH 入口
                 VPS 指定回环端口 → Windows 127.0.0.1:22
VPS 应用 SSH 客户端 → 上述端口 → Windows 专用账户
```

反向隧道和执行 SSH 是两个认证角色，不能把 Windows→VPS 的普通 SSH 会话误认为 VPS 已能登录 Windows。VPS 可直连 Windows 的场景允许手动连接配置；默认流程面向应用管理的反向隧道。

当前部署可能采用账号容器。反向监听端口与 SSH 适配器必须处在可互通的指定网络命名空间，不能假定容器内 `127.0.0.1` 就是 VPS 宿主回环。优先将 SSH 客户端放在应用服务侧、让 CC 只调用已有进程内工具；部署时使受限转发端点在该服务侧可达，且不公开绑定公网。

### 3.2 复用现有工具边界，增加一种传输

保留现有云端实现，新增独立的 SSH 传输模块。按服务端解析的项目目标分派，而不是让模型判断该在哪台机器执行。

- 云端项目：原来的云端身份、容器和文件操作路径。
- SSH 项目：SSH 文件操作与 Windows 命令执行。
- SSH 连接失败必须抛出明确错误，不能返回“未绑定”从而落到 Node 本机文件系统或云端命令。

Windows 端使用随桌面安装包提供的小型 PowerShell 辅助脚本，按 SSH exec 请求运行、经标准输入接收结构化参数、经标准输出返回结果；不是后台服务。不把路径、文件内容或 JSON 拼入 Shell 命令。辅助脚本位于安装/配置目录而非项目内。首次配置需要确认 SSH 登录账户能够读取该脚本。

该脚本负责确定项目内路径、列目录、读取、写入、搜索、文件管理和受跟踪的命令运行。写入使用读取时的哈希检查，检测编辑器与 CC 的已知内容冲突；测试实际 Windows 文件共享/锁行为，不把单独的“先读哈希、后覆盖”宣称为原子写入。保持 UTF-8、二进制内容和换行不被 SSH 输出编码破坏。

### 3.3 项目身份与连接配置

新增独立于 `workspace_mode` 的位置字段，暂定 `sourceMode: cloud | ssh`。现有 `shared / isolated` 仍表示会话隔离方式，不承担位置含义。

- 旧项目与不传新字段的 API 默认 `cloud`，无需配置 SSH。
- 增加项目目标记录，关联 `projectId`、连接 ID、设备 ID、Windows 根目录、目标平台、默认 Shell、绑定代际。
- 现有 `project_path` 对 SSH 项目保留为 VPS 上的稳定会话/元数据锚点，保护会话外键和恢复逻辑；锚点不保存源码，也不允许作为源文件目录执行。
- Windows 根目录独立保存，由 Windows 端解析；CC 文件工具使用项目相对路径或虚拟项目根，避免暴露不必要的个人路径。
- 工作区描述增加来源、连接状态与能力；旧云端响应兼容。现有 `cloudReplica` 字段在旧 API 中保留兼容，新逻辑依据明确来源而非字段名称推断执行位置。
- SSH 第一版固定为共享本地目录；多个会话可保留独立聊天，但应用内同一目录的写入任务串行。不同项目入口指向同一物理目录时也应识别并协调。人工 IDE/外部进程不受应用写锁约束，通过文件冲突检查降低覆盖风险。
- 第一版不提供项目原地切换执行位置。要同时保留本地和云端版本，创建两个独立项目入口；连接重配需空闲状态、更新代际并重新验证，旧请求不得漂移到新目标。
- 会话固定目标 ID 与代际；发送、编辑重跑、恢复、分叉、排队消息和定时消息都复核该身份。连接设置变化不能将旧对话无提示地绑定到另一目录或另一台电脑。

### 3.4 SSH 与凭据

- Windows 用专用普通账户登录；检查它对项目和所需 SDK 的访问权限。
- 访问其他文件的实际边界是该账户的 NTFS 权限。工作目录和工具路径校验不是进程沙箱，第一版不承诺“只能访问项目目录”。
- Windows→VPS 隧道密钥与 VPS→Windows 执行密钥分离，均位于项目外。SSH 私钥不进入 React 状态、项目工具结果、日志或 CC 上下文。
- VPS 上只向应用服务提供执行凭据，CC 仍在 VPS 使用现有认证；不增加 `--bare` 或更换现有模型认证流程。
- 两个方向固定 SSH 主机指纹；不使用关闭主机校验或自动忽略指纹变化的配置。
- 云端账号连接与 SSH 连接分开管理：云端登录成功不隐式启用 SSH，SSH 不可用不阻断云端项目。
- 自托管部署可先配置受限 SSH 入口；托管部署需要账号级的公钥登记、监听端点分配和撤销能力。缺少此部署能力时明确显示不可用，不能复用已停用的同步容器或假装隧道已存在。

## 4. 用户操作流程

1. 保持现有登录流程。新建项目新增“云端 VPS / SSH 本地”两项，默认云端。
2. 选云端时保持当前服务器目录与 Git 克隆流程。
3. 选 SSH 本地时选择连接、Windows 项目目录；桌面端提供本地文件夹选择。第一版接入已有目录，本地 Git 克隆可从命令终端完成。
4. 首次配置检查：Windows SSH 服务、登录公钥、主机指纹、目录权限、PowerShell、Git/所需构建工具，并进行真实的 SSH 身份与目录探测。
5. 显示“本地目录 / 在线状态 / Windows 命令环境”；选择项目后，CC、文件树、Git 和终端一致指向该绑定。
6. 断线显示本地离线、阻止新的文件/执行请求；重连验证设备、账户、项目根与代际后才恢复。
7. 退出登录、切换账号、关闭应用只清理本应用拥有的隧道和任务，不停止系统 sshd、不杀所有 ssh 进程、不修改其他连接。

## 5. 分阶段实施

### 阶段一：身份、部署契约与 SSH 最小链路

- 记录当前代码基线，明确部署中应用服务、CC 和 sshd 的网络位置。
- 新增项目来源、连接档案和目标绑定的增量数据库迁移；现有云端数据保留。
- 新增 VPS SSH 适配器：主机校验、密钥引用、连接复用、探活、超时与连接错误分类。
- MyGo 增加新命名的 SSH 配置/目录选择/隧道启停/状态接口，保留旧同步兼容 RPC 的停用行为。
- 提供受限 VPS SSH 入口的部署步骤与 Windows SSH 首次配置说明；云端模式不依赖这些步骤。Windows 反向连接场景只需要回环 SSH 服务，不默认开放局域网/公网入站；第一版不自动安装系统服务、创建账户或放宽防火墙。
- 完成 Windows 辅助脚本和非敏感探测：实际 Windows 身份、平台、根目录与读取能力。

完成条件：VPS 能经指定连接读取本地测试目录与执行命令，断线和错误指纹可准确识别；纯云端登录无 SSH 依赖。

### 阶段二：让 VPS CC 真正使用本地项目

- 在 `workspaceQuery` / 工作区解析入口加入显式 SSH 分支，避免经过云端绑定初始化、工作树快照和容器执行。
- 复用现有 CC 项目工具外观，连接 SSH 的 list/read/write/search/exec 实现；提示词和工具描述明确 Windows / PowerShell，不声称本地存在 Linux `/workspace` 目录。
- CC 在 VPS 元数据目录启动，保持原有认证与会话记录；内置 VPS 文件/命令工具不能绕过项目目标。
- 文件改动采用哈希冲突检查；结构化路径映射覆盖空格、中文、引号和二进制内容。
- SSH 环境不具备云端只读挂载的保证。计划/只读会话第一版仅开放文件检查工具，禁用任意命令执行；不能把 `run_command(readOnly=true)` 描述为 Windows 上的强制只读。常规开发会话的命令依照 Windows 账户权限执行。
- 命令返回实际 stdout/stderr/退出码，支持输出限额、超时和停止。记录任务身份，SSH 断开不能被当作远端已停止；清理未确认时阻止重放写入命令和新的冲突任务，提供检查/停止原任务入口。Windows Job Object / 进程组管理只用于正常任务的生命周期与资源控制，不宣称能够隔离恶意代码或撤销它在其他位置留下的状态。
- SSH 项目只开放已适配的 Claude；其他提供商在该模式明确不可用，云端行为保持。

完成条件：用户从聊天让 CC 读取代码、修改文件、编译、运行命令行程序、测试并处理真实失败，操作实际发生在 Windows；CC 仍只在 VPS 运行。

### 阶段三：接入产品界面

- 新建项目与连接设置增加来源选择、连接检测、设备/目录信息和在线状态。
- 文件树、编辑器与文件引用使用同一个目标；预览/下载必须经 SSH，不能读取元数据锚点下的同名文件。
- Git 面板通过 SSH 使用 Windows Git，验证仓库根、状态、diff、历史、暂存、提交和分支；不依赖 VPS Git 仓库存在。
- 终端接入 Windows SSH 会话，保留输入、输出、退出状态；探测伪终端能力，不支持时明确为命令管道。该终端不在 Windows 启动 CC 或其他 AI 提供商。
- 本地会话隐藏云端隔离工作区/集成按钮与云端预览入口；云端项目完整保留这些功能。
- 支持本地读取到的文件/图片引用与错误定位，不强行将 Windows 路径交给 Linux 附件读取逻辑。
- 调整计划任务、斜杠命令、技能/项目说明、任务面板与插件入口的能力检查：经过同一目标解析；尚未适配者明确禁用，不能误操作 VPS。
- 删除 SSH 项目默认只删除应用记录/连接关联，不删除本地源目录。

完成条件：从项目列表打开 SSH 项目后，聊天、文件、Git、终端指向同一台电脑的同一目录；原云端项目操作无变化。

### 阶段四：回归、打包与交付

- 更新 MyGo 接口绑定、安装包资源及来源说明，打包辅助脚本；不恢复 Mutagen、Pi 或旧同步接口。
- 更新当前“纯云端”说明为“默认云端，按项目选择 SSH”，保留旧同步迁移的历史边界。
- 运行相关模块测试、前后端类型检查/构建/lint、Go 原生检查和安装包检查。
- Windows + Linux VPS 的真实链路验收使用专用测试目录，生产部署和安装包发布在实现验证后单独进行。

## 7. 验收标准

| 场景 | 必须验证的结果 |
| --- | --- |
| 仅云端、未配置 SSH | 登录、恢复、聊天、文件、Git、终端、隔离与集成保持原行为；不启动 SSH |
| 入口与认证 | 开发模式、自动化测试和发布产物均进入同一个已适配运行实现；VPS 现有 CC 登录/模型连接可继续使用 |
| SSH 开发闭环 | VPS CC 读改本地文件、运行 Windows 构建和测试，退出码与实际文件一致 |
| 计划/只读会话 | 可以读取项目，拒绝文件修改和任意命令；不把命令的自报只读标志当作 OS 约束 |
| 来源隔离 | VPS 放置同名诱饵文件，SSH 请求仍只访问本地；离线不读诱饵、不在 VPS 构建 |
| 路径与内容 | 中文/空格/引号路径、UTF-8、CRLF、二进制、缺失文件、符号链接/junction 与项目越界 |
| 文件冲突 | 外部编辑后，旧哈希写入失败并保留新内容 |
| 身份隔离 | 不同设备的相同路径不同身份；账号/设备/项目重绑使旧请求失效 |
| 连接异常 | 密钥错误、主机指纹变化、端口占用、断网/休眠/重连均有明确状态，不自动接受新身份 |
| 任务结束 | 超时、取消、断线后查询真实远端状态；未确认结束前不报成功、不盲目重跑 |
| UI 一致性 | 同一项目的聊天、文件、Git、终端与引用一致；切换项目不会收到旧项目响应 |
| 权限与数据 | 构建账户无法读取已用 ACL 保护的测试秘密文件；密钥不出现在 CC、前端与日志 |
| 生命周期 | 关闭/切换只停止本应用隧道；恢复不启动旧同步；删除项目不删除本地目录 |
| 部署网络 | 按实际账号容器拓扑连接成功，SSH 转发不暴露公网，不泄露其他账户端点 |

实现完成记录：项目来源、服务端目标/会话代际、SSH 文件/命令传输、Windows 辅助脚本、CC 工具、文件/Git/命令控制台、桌面隧道及 UI 已接通。云端维持默认。开发 tsx 入口与编译后的 Claude 运行入口均已核验；辅助脚本已嵌入原生验证构建。

自动化验证包括云端回归、VPS 同名诱饵不回退、SSH 只读/并发/清理/恢复、账号与历史订阅隔离、Windows 本机真实文件和进程、路径与哈希冲突、原生生命周期，以及前后端类型检查和构建。后续隔离实机验收已完成真实反向 SSH 与 Windows 公钥登录、文件/Git/npm 测试与构建、图片、VPS CC 项目工具、启动前与运行中取消、强制终止隔离服务后的精确回执恢复，以及原生隧道启停/清理；实测修复 `ProgramData` 环境缺失和启动前取消竞态。Windows 使用临时回环 sshd，原生测试仅注入服务前置检查结果并使用测试账号作用域，不能替代正式登录/UI、专用账户 ACL、生产账号网络和休眠/长断网验收。本轮没有安装系统 sshd、修改系统账户/防火墙或发布生产。

第一版采用逐行 Windows 命令控制台；没有完整 PTY。对同账号的物理卷/目录身份保守去重，阻止通过连接别名重复登记；磁盘克隆产生身份碰撞时会拒绝登记，后续可使用服务端主机公钥身份进一步区分。密钥与连接目录仍由部署者准备，托管环境没有分配端点时明确不可用。
